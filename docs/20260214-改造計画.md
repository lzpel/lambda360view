ブラウザ側で色寸法、穴の位置や数を変えたいなどの要望があったときに、サーバーで形状を再計算しフロントエンドに反映する仕組みを構築したい

速度が大事なので現状のjson渡しは容量やパース時間がネックになる

そこで現状のjson渡しは残しつつglb渡しを許したい

{ "meshes": [ { "name": "part_A", "extras": {　ここにいれる } }。。。 ] }

今はPartにShapeDataを持たせているが、Part=Shape+Extraにして
Extraはglbのjsonパートのextrasにそのまま突っ込む

lambda360viewはjson渡しglb渡しを両方読み込み両方同じパイプラインで表示する

## 実現可能性評価 (2025-02-15 Claude調査)

### 結論: 実装可能

既存のスタックとの相性が良く、段階的に実装できる。

### 現状の構造

```
Lambda360ViewProps.model: ModelData
  └─ parts: Part[]
       ├─ shape?: ShapeData (vertices, normals, triangles, edges)
       ├─ color, alpha, loc, id, name, ...
       └─ parts?: Part[] (再帰)
```

レンダリングパイプライン: `ModelData → ModelRenderer → PartGroup(再帰) → PartMesh(BufferGeometry生成)`

### GLB対応が有利な点

1. **Three.jsのGLTFLoaderがGLBをパースしてBufferGeometryを直接返す** — 現在のPartMeshが既にBufferGeometryベースなので、パイプラインの後半はそのまま使える
2. **@react-three/drei(既に依存済み)にuseGLTFフックがある** — 追加依存なし
3. **glTF 2.0仕様でextrasフィールドが公式サポート** — mesh/nodeレベルにメタデータ(id, name, color, alpha等)を格納可能
4. **GLBはバイナリ形式** — JSONに比べてファイルサイズ削減(30-50%)、パース時間大幅短縮。TypedArrayをそのままメモリマップできる
5. **glTFのシーングラフ(node hierarchy)がPartの親子構造にマッピング可能**

### 課題と対策

| 課題 | 詳細 | 対策 |
|------|------|------|
| **エッジデータ** | glTFにはCADエッジ(線分)の概念がない。現在のShapeData.edgesは事前計算済みの線分配列 | extrasにエッジデータをBase64またはバイナリbufferViewとして格納する。GLTFLoader拡張(registerPlugin)で取得 |
| **マテリアル** | GLBはPBRマテリアル。ビューアはmeshBasicMaterial(フラットCAD風) | GLBのマテリアルは無視し、extrasのcolor/alphaからmeshBasicMaterialを生成(現状と同じ) |
| **face_types等の付加情報** | ShapeDataのobj_vertices, face_types, edge_types等はglTFに存在しない | extrasまたはカスタムbufferViewに格納 |
| **BoundingBox** | ModelDataレベルのbbが必要 | GLBシーン全体からTHREE.Box3で自動計算するか、シーンルートのextrasに格納 |

### 提案する型の変更

```typescript
// Part = Shape + Extra に分離
interface Part {
    id: string;
    name: string;
    type: string;
    subtype?: string;
    shape?: ShapeData;              // JSON渡しのときに使う
    geometry?: THREE.BufferGeometry; // GLB渡しのときに使う(パース済み)
    color?: string;
    alpha?: number;
    loc?: Location;
    parts?: Part[];
    // ... 既存フィールド
    extras?: Record<string, unknown>; // GLBのextrasをそのまま保持
}
```

### 実装ステップ案

#### Phase 1: GLBローダー追加
- `src/loaders/glbLoader.ts` を新設
- GLBをパースしてModelData形式に変換する関数 `loadGlb(url | ArrayBuffer): Promise<ModelData>`
- extrasからcolor, alpha, id, name等を復元
- エッジデータをextrasから復元

#### Phase 2: PartMeshの二系統対応
- PartMeshが `shape(ShapeData)` と `geometry(BufferGeometry)` の両方を受け付けるようにする
- GLBの場合はGLTFLoaderが生成したBufferGeometryをそのまま利用(パフォーマンス向上)

#### Phase 3: Lambda360ViewPropsの拡張
```typescript
interface Lambda360ViewProps {
    model?: ModelData;        // 既存JSON渡し
    glbUrl?: string;          // GLB URLを渡す
    glbData?: ArrayBuffer;    // GLBバイナリを直接渡す
    // ... 既存props
}
```

#### Phase 4: サーバー連携
- パラメータ変更 → サーバーにリクエスト → GLBレスポンス → フロント更新
- ArrayBuffer直接渡しが使えるので、fetch → arrayBuffer() → glbData propsで高速反映

### サイズ・速度の見積もり

現在のhexapod.jsサンプル(28.5KB)レベルのモデルの場合:
- JSON: パース時間 + Float32Array再構築のオーバーヘッド
- GLB: バイナリから直接TypedArrayを参照可能、パース時間は数ms程度

大規模モデル(数MB〜数十MB)になるほどGLBの優位性が増す。

### サーバー側GLB生成について

このライブラリのスコープ外だが、参考として:
- Python: `pygltflib` や `trimesh` でGLBを生成可能
- Node.js: `gltf-transform` でプログラマティックにGLBを組み立て可能
- extrasフィールドへのメタデータ付与はいずれのライブラリでもサポート済み
