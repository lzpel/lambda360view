3. 改造

そこで現状のjson渡しは廃止しglb渡しを許したい

    /** GLB binary data (ArrayBuffer) to load directly */

にモデルインプットのtypeを変更する

GLBのメタデータ（extras）に

    /** エッジ頂点座標 (LineSegments の描画に使用) */
    edges: Float32Array;

が入っている場合、それを元にエッジを描画する

4. 設計方針

4.1 GLBをシーングラフの唯一の真とする（Part再帰ツリーのstateを持たない）

GLTFLoaderが返す scene (THREE.Group) をそのままThree.jsのシーングラフとして描画する。
現状の ModelData → Part[] → PartGroup再帰 → PartMesh の流れを廃止し、
GLBから得られたsceneを直接レンダリングする。

理由:
- Part[]という中間stateを持つと、GLBとの同期コストが発生する
- GLTFLoaderは既にノード階層・transform・materialを解決済みのTHREE.Groupを返す
- 色・透明度・位置・回転はGLB内のmaterial/transformとして保持されている
- 必要に応じてscene.traverse()でノード情報を取得すればよい

4.2 BoundingBoxの算出

現状の ModelData.bb は廃止する。
GLBロード後に THREE.Box3().setFromObject(scene) で算出する。

4.3 エッジデータのGLB内格納方式

glTF仕様の extras フィールドを使用する。
GLTFLoaderはextrasの内容を各ノードの userData に格納する。

格納方式の選択肢:
  (a) extras にbase64エンコードしたFloat32Arrayを格納
      → シンプルだがバイナリ効率が悪い（約33%増）
  (b) GLBのbufferView/accessorとしてバイナリ格納し、extrasからインデックスで参照
      → バイナリ効率は最良だが、GLTFLoader標準のパースでは自動展開されない
         カスタムのGLTF extensionまたはpost-processing で手動デコードが必要
  (c) extrasに頂点座標を数値配列として直接格納
      → JSON部分が大きくなるがデコード不要で最もシンプル

→ まずは (c) で実装し、パフォーマンス問題が出たら (b) に移行する方針とする
  mesh.userData.edges が number[] として存在すれば new Float32Array(edges) で変換しLineSegmentsを描画

4.4 旧式ModelData → GLB変換ヘルパーは実装しない

旧式データの変換はスコープ外とする。GLB生成はサーバー側の責務とする。
